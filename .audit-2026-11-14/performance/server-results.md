# 服务端性能测量结果（2026-11-14）

正常使用相关的热接口很快，本轮没有请求失败，也没有观察到重复操作后的持续内存增长。两个明确值得优化的体验点是完整启动耗时，以及工作区模型目录参与并发时的延迟。本轮只测量和审查，未修改产品代码。

## 内存、句柄与后台成本

每 2 秒采样 launcher 与所有后代：工作集（RSS）、私有提交量、句柄、线程、累计 CPU 时间；同时读系统空闲 RAM 和 `GetSystemTimes`。主测量 105 个有效样本，无采样错误。采样本身 p50/p95 为 29.7/46.1 ms，会带来小量干扰；2 秒间隔可能漏掉短峰值。

私有提交量与工作集分开报告，**不相加**。主测量私有提交峰值 471.0 MiB，工作集峰值 462.2 MiB；系统最低可用 4.38 GiB，未触及 1.5 GiB 进程树/1 GiB 系统可用的停止阈值。主测量背景整机 CPU 均值 7.3%。

CPU 的两个口径明确区分：系统字段是**28 个逻辑处理器合计的整机百分比**；服务进程树由累计 CPU 时间差计算，100% 单核等价表示占满一个逻辑处理器。

- 60 秒会话轮询＋健康探针：服务约 6.04% 单核等价，约 0.216% 整机等价。
- 只有 250 ms 健康探针：约 1.22% 单核等价，约 0.044% 整机等价。
- 新进程真正无 HTTP：约 0.61% 单核等价，约 0.022% 整机等价；该时段背景整机 CPU 均值 15.2%，与前一阶段的背景负载不同。

## 只读代码热点与结论边界

- `src/lib/agent-manager.ts:375` 在切历史页之前先构造整个分支的展示消息；`getManaged` 在冷打开时同步解析会话，`registerManaged` 遍历 entries。21.6 MB fixture 首次读取约 95 ms、后续分页 p95 13 ms，本轮通过 1 秒目标；更大文件的线性成本仍应保留关注，不能仅因响应页有 100 条就认定计算有界。
- `src/lib/session-reader.ts` 列表 1.2 秒 TTL 到期后仍需枚举/stat；`src/app/api/sessions/route.ts` 即使最后返回 304，仍先规范化、排序/合并并生成 ETag。本轮 300 会话跨 TTL p95 72 ms，通过目标。
- `src/lib/files-service.ts:150` 缓存有效 2 秒、最多 16 工作区，失效后重新执行有界 Git 列举。本轮 10k 文件首次 204 ms、跨 TTL p95 176 ms，通过目标。
- `src/lib/pi.ts:91/273/478` 的工作区 settings/loader/package-manager Map 未见按工作区数回收；40 工作区一次循环不足以判为泄漏。冷会话池已限制 64，不应将缓存存活本身当成泄漏。
- 本轮没有真实模型生成、工具执行、联网插件安装、真实手机、多人网络或长期浸泡测试；不能据此推算远程用户的交互分位数。
