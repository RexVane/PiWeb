- 构建、服务端压力和浏览器测量分开进行。生产构建时间只记录为开发/发布成本，不作为日常启动时间。
- 桌面 1280×800；移动视窗 390×844。CPU/网络节流单独标明为模拟环境，不称真手机测试。

## 测量前预算

| 项目 | 本轮比较依据 |
| --- | --- |
| LCP / CLS | 参考 Core Web Vitals 的良好阈值：2.5 秒 / 0.1；本地实验室重复测量不能证明真实用户第 75 百分位合格 |
| 操作响应 | 点击、输入、面板/会话切换到可见响应 p95 ≤ 200 ms，作为本项目实验室目标；不将脚本执行时间或单次交互直接称为 INP |
| 滚动 | 可见页面 requestAnimationFrame 间隔 p95 ≤ 33.3 ms，>50 ms 长帧占比 ≤5%，为本轮自定预算；另记录 >50 ms 主线程任务，避免仅报平均 FPS |
| 轻量 API | 已预热串行请求 p95 ≤200 ms；首次初始化、搜索、完整目录索引和长历史单列，重操作以1秒内为目标，不与轻量缓存命中混算 |
| 启动 | 三次实际生产启动分别记录 health 就绪、首个认证请求及首页；3秒可用作为本轮本机体验目标，包含/排除初始化需明确 |
| 内存 | 分开报告服务进程树工作集/私有提交量与浏览器 JS heap/DOM，绝不混作同一个指标；没有统一行业内存上限，重点看空闲成本、负载峰值及重复操作后是否持续增长 |
| 内存重复操作 | 预热后至少50次切换/开关，比较强制GC后的JS heap与DOM基线；超过 max(32 MiB, 基线10%) 且继续增长时追加调查，单次增长不能直接判内存泄漏 |

LCP、CLS、INP阈值参考 Google web.dev 的 Web Vitals / INP 文档；Chrome DevTools 的 Fix memory problems 文档区分 OS footprint、JS heap 与 GC 后存活量。上述滚动、API、启动和增长预算是本轮工程目标，并非浏览器官方统一标准。

## 负载与证据

- 空/轻载首页冷、热导航各至少5次；面板/输入操作至少20次，报告p50/p95和样本量。
- 合成300会话、10k消息长会话、10k文件项目；资源工作区和会话反复打开需设内存上限，避免压垮16GB测试机。
- 服务端记录成功率、响应体大小、阶段耗时、内存/句柄和健康请求延迟；浏览器记录FCP/LCP/TTFB/CLS、资源传输、长任务、帧间隔、交互可见延迟、JS heap与DOM。
- 模拟流式消息若使用拦截数据，必须与真实后端会话、真实文件接口分开标注。
- 原始JSON/日志与结论保存在本目录；自建探针与stage使用完后回收，保留审查证据。
