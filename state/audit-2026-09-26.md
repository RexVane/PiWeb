## Findings

### 1. P1 - Deleting a root-level skill can recursively delete its entire collection

Location: [skills-service.ts:148](D:/AIApp/PiWeb/src/lib/skills-service.ts:148), [skills-service.ts:152](D:/AIApp/PiWeb/src/lib/skills-service.ts:152).

Status: pre-existing backend defect; reproduced with the real deletion function and an intercepted filesystem removal.

`deleteSkill` derives the directory from the authorized `SKILL.md`. Matching a known collection root does not reject deletion: it skips the only guard and reaches `fs.rm(skillDir, { recursive: true, force: true })`. For other paths, `path.basename(skillDir) === ""` does not identify an ordinary workspace root such as `D:/repo`.

The installed SDK accepts a directory's own `SKILL.md` as a skill. Consequently, a root-level skill in the global collection is a valid discovery result, not just a forged arbitrary path. An explicitly configured root-level project skill can also make the project directory a deletion candidate.

Evidence: a temporary `agentDir/skills/SKILL.md` was exposed through a mocked discovery result. Calling the actual `deleteSkill` attempted recursive removal of `agentDir/skills`. The `fs.rm` call was intercepted; no real skill collection was deleted. Existing child-directory deletion tests do not cover collection or workspace roots.

Recommendation: explicitly reject canonical collection roots, workspace roots, the agent directory and other protected ancestors. Define file-only deletion semantics for root-level skills if they must remain deletable. Add tests for global collection roots and configured workspace-root skills.

### 2. P1 - Windows case aliases bypass swarm protection for Git metadata

Location: [swarm-service.ts:103](D:/AIApp/PiWeb/src/lib/swarm-service.ts:103), [swarm-service.ts:257](D:/AIApp/PiWeb/src/lib/swarm-service.ts:257).

Status: pre-existing backend defect; reproduced on Windows, including a real temporary Git worktree.

The path guard compares components with exact `.git` and `node_modules` spellings. Windows resolves `.GIT` to the same metadata file, but the guard accepts it. The subsequent realpath containment check does not recheck protected metadata, because the metadata pointer itself is inside the worktree.

Evidence: literal `.git` was rejected, while `.GIT` was accepted and read the same file. In a disposable repository configured with `core.hideDotFiles=false`, the accepted `.GIT` pointer was rewritten to the main repository's `.git`. Running the service's subsequent `git add -N -- .` operation from the worktree added a worker-only file to the main repository's index before patch acceptance. No main-workspace file or real user repository was changed.

Important qualification: a first overwrite attempt against Git's default hidden Windows pointer failed with `EPERM`. The full reproduction used the supported no-hidden configuration. The application must not treat an incidental filesystem attribute as its isolation boundary.

Recommendation: normalize protected path components using platform-appropriate comparison and validate canonical protected targets as well. Reject aliases to Git metadata/dependency directories. Add a real Windows worktree regression proving that the main index cannot change before acceptance.

### 3. P1 - The UI promises an OS sandbox and network isolation that do not exist

Location: [TestInspectorPod.tsx:370](D:/AIApp/PiWeb/src/components/TestInspectorPod.tsx:370), [TestInspectorPod.tsx:528](D:/AIApp/PiWeb/src/components/TestInspectorPod.tsx:528), [test-run-service.ts:94](D:/AIApp/PiWeb/src/lib/test-run-service.ts:94).

Status: introduced in the current UI changes; execution-model mismatch established by source inspection.

The test inspector claims complete isolation and that `PI_OFFLINE=1` completely blocks external requests. The backend instead starts an ordinary Node/Vitest child process in the actual trusted workspace and spreads the server's environment into it. There is no OS filesystem sandbox, network firewall or credential isolation, and this function does not itself set `PI_OFFLINE`.

Project trust is checked before execution, but trust is not isolation. Test code can perform ordinary Node filesystem/network operations and read inherited environment variables. A cooperative application flag is not a general restriction on arbitrary test code. Main-session sandbox-ready wording is similarly inconsistent with the ordinary bash/edit/write tools and the existing settings warning that no system sandbox is provided.

Evidence: backend process-launch options were inspected; a UI probe also confirmed the isolation badge renders even before a test run. No destructive or network-exfiltration payload was executed.

Recommendation: remove unsupported security promises and state the actual execution/credential model. If a real sandbox is intended, implement and verify that boundary before advertising it. Add copy/capability tests so UI assurances cannot diverge from backend capabilities.

### 4. P2 - Test coverage, memory and worker details are fabricated

Location: [TestInspectorPod.tsx:193](D:/AIApp/PiWeb/src/components/TestInspectorPod.tsx:193), [TestInspectorPod.tsx:268](D:/AIApp/PiWeb/src/components/TestInspectorPod.tsx:268), [TestInspectorPod.tsx:541](D:/AIApp/PiWeb/src/components/TestInspectorPod.tsx:541).

Status: introduced in the current UI changes; reproduced in a component test.

Coverage values `94.2%` and `88.5%`, memory `48.2 MB`, worker PIDs `48211`/`48212`, pool size, test round and `Vitest v1.4.0` are literals, not backend results. The API result type does not contain these metrics. The current repository actually runs Vitest `5.0.0`, and another workspace can have a different version.

Evidence: with an empty test catalog and no completed run, the component still displayed the coverage and memory values. This creates a false impression of measured test quality and live execution state.

Recommendation: hide unavailable metrics or label them as unavailable. Populate them only from actual reports and process data. Add negative tests asserting that no-run and unsupported-report states do not show measurements.

### 5. P2 - A single-file test request can execute additional test files

Location: [test-run-service.ts:94](D:/AIApp/PiWeb/src/lib/test-run-service.ts:94).

Status: pre-existing backend defect; reproduced against installed Vitest `5.0.0`.

Vitest's positional filename argument is a substring filter, not an exact file selection. Passing `tests/a.test.ts` can also select `tests/a.test.tsx` or a nested path containing the same filter. The API then reports the requested filename alongside combined test results, and unintended tests can execute side effects.

Evidence: `vitest list tests/audit-review.test.ts --filesOnly` returned both temporary `.ts` and `.tsx` probe files. Running the same positional filter executed both files, seven tests in total. Both files were removed afterward.

Reference: [Vitest Test Filtering](https://main.vitest.dev/guide/filtering).

Recommendation: enforce an exact discovery include using the installed runner's supported configuration/API while preserving the user's relevant config. Do not assume an absolute positional path fixes matching. Add colliding `.ts`/`.tsx` and nested-path fixtures and verify only the requested file executes.

### 6. P2 - A late prompt-panel response can replace the current workspace's data

Location: [PromptPanel.tsx:75](D:/AIApp/PiWeb/src/components/PromptPanel.tsx:75), [PromptPanel.tsx:84](D:/AIApp/PiWeb/src/components/PromptPanel.tsx:84), [PromptPanel.tsx:128](D:/AIApp/PiWeb/src/components/PromptPanel.tsx:128).

Status: existing request-ownership defect in a currently modified component; reproduced in jsdom.

Catalog loading has no abort/generation/current-owner guard. A request for an old cwd or session can resolve after the current request and overwrite the active sources, assembled prompt and tool information. File-content callbacks also have no ownership check after awaiting the response. Refreshes can race even without a workspace change.

Evidence: defer the old workspace response, rerender with a new cwd, resolve the new catalog, then resolve the old catalog. The component switched back from `new.md` to `old.md`. No model was called.

Recommendation: key each request to cwd/session and a generation, abort superseded requests, clear stale data on ownership changes, and guard delayed file-opening callbacks. Cover delayed old catalogs and reads in regression tests.

### 7. P2 - Concurrent imports share a temporary file and race idempotency checks

Location: [writer.ts:238](D:/AIApp/PiWeb/src/lib/session-import/writer.ts:238), [session-import/index.ts:179](D:/AIApp/PiWeb/src/lib/session-import/index.ts:179).

Status: pre-existing backend defect; deterministic writer interleaving reproduced.

The temporary name is `${target}.${process.pid}.tmp`. Two requests importing the same source/external ID in one server process use the same target and temporary path. The earlier imported-session lookup is not protected by a cross-request lock. Writes can overwrite each other, and a rename can consume the shared temporary file before the other request renames it.

Evidence: two actual writer calls were synchronized at rename after both writes. Both used an identical temporary pathname. Allowing the first rename to finish before the second made one import reject. The scheduling barrier made this deterministic; this was not a full concurrent HTTP-import test. All files were temporary fixtures.

Recommendation: lock the source/external-ID check-and-write operation, use unique exclusively created temporary files and make target creation/idempotency atomic. Add concurrent same-process tests and account for multi-process deployment if supported.

### 8. P2 - Cancelling the Windows folder dialog can open it again

Location: [pick-folder.ps1:95](D:/AIApp/PiWeb/scripts/pick-folder.ps1:95).

Status: introduced in the current script changes; source/API-contract finding, not a manual GUI reproduction.

Any nonzero result from `Show(hwnd)` retries `Show(IntPtr.Zero)` when there is a foreground window. Normal user cancellation is also a nonzero result, so cancelling the owned dialog can immediately open an unowned second dialog. This turns cancellation into a retry instead of terminating the action.

Reference: [Microsoft IModalWindow::Show](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-imodalwindow-show) specifies `HRESULT_FROM_WIN32(ERROR_CANCELLED)` for cancellation.

Recommendation: return immediately on the cancellation result. Retry without an owner only for explicitly identified owner-related failures. Verify cancel, confirm and owner-failure paths on Windows.

### 9. P2 - Global text-selection disabling breaks partial chat/code copying

Location: [layout.tsx:31](D:/AIApp/PiWeb/src/app/layout.tsx:31), [AppShell.tsx:676](D:/AIApp/PiWeb/src/components/AppShell.tsx:676).

Status: introduced in the current UI changes; source/CSS-behavior finding, not a live browser drag test.

Both the body and shell use `select-none`. Ordinary chat Markdown and rendered code have no selection override, so users cannot select a sentence, a code fragment or an error substring. The whole-message copy button still works; this is specifically a partial-selection regression, not a claim that all copying is broken.

Reference: [MDN user-select](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/user-select) explains how a parent's `none` affects descendants whose value is `auto`.

Recommendation: scope nonselection to chrome/drag controls and explicitly enable selection for message bodies, code, diffs and error details. Add a real-browser selection test rather than relying only on jsdom.

### 10. P2 - The update idle gate ignores running swarm and test jobs

Location: [update/route.ts:21](D:/AIApp/PiWeb/src/app/api/update/route.ts:21), [agent-manager.ts:1663](D:/AIApp/PiWeb/src/lib/agent-manager.ts:1663), [swarm-service.ts:241](D:/AIApp/PiWeb/src/lib/swarm-service.ts:241).

Status: existing integration gap; static finding, no package update executed.

The updater checks only streaming sessions tracked by `agent-manager.activeStatus`. Swarm sessions are created separately, and test runs use their own running set. An otherwise idle main session therefore passes the gate while swarm/test work remains active. Dependency replacement or update preparation can proceed concurrently with work that still uses the current runtime.

There is also no common maintenance barrier preventing new work from starting after an idle check. The UI's instruction not to start another task is not a backend exclusion guarantee.

Recommendation: use a shared activity/maintenance coordinator for main sessions, swarm tasks and test runs. Make entry into update mode atomic and reject new work until the update phase ends. Test all active-job categories without actually installing packages.
